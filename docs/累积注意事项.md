# 目录结构说明

```
  HoneyGhost/
  ├── Makefile              # 顶层唯一构建入口：agent / ebpf / go / test / image / package
  ├── CMakeLists.txt        # C++ 目标定义
  ├── go.work               # 不进版本控制，由 scripts/gen-go-work.sh 生成
  ├── scripts/              # 仓库级脚本（生成 go.work 等）
  ├── proto/
  │   ├── internal/         # 待建：file_event, syscall_event —— 仅 C++，不过 wire
  │   ├── agent_bridge/     # 待建：现 role_containerd_bridge.proto
  │   ├── agent_central/    # 待建：跨节点契约
  │   └── cli/              # 待建
  ├── agent/                # 节点代理：一个 DaemonSet Pod / 一份 systemd unit = 一次部署
  │   ├── main.cc
  │   ├── control_plane/ collector/ detector/ semantic/ context_maintainer/ event_data/ util/
  │   │   ├── include/      # 对外头：别的模块可以 include
  │   │   └── src/          # 私有头与源文件；子模块再嵌一层（如 context_maintainer/src/rule/）
  │   └── role_discovery/   # 与 control_plane 同级；内含 Go module containerd_bridge/
  ├── central/              # 待建：Go module
  ├── cli/                  # 待建：Go module
  ├── gen/go/               # 待建：Go module（共享）—— proto 的 Go 产物需被多个 module 共享时放这里
  ├── kernel/               # eBPF：探针、共用头与 CMakeLists.txt
  ├── test/
  └── deploy/
      ├── k8s/              # 待建：daemonset-agent.yaml（含 bridge sidecar）, central.yaml
      ├── baremetal/        # 待建：systemd unit, install.sh
      └── docker/           # 待建
```

1) 模块布局固定为 `include/`（对外头）+ `src/`（私有头与源文件）。**`include/` 下的头不得引用 `src/` 下的头**，这是该布局的全部意义；否则私有等同于公开。
2) 公共头需要私有类型时用前置声明，并把该类型定义在 `src/` 的上位 `hng::detail` 命名空间下（见 `context_maintainer.hpp` 对 `PendingTable` / `DeriveVerdict` 的处理）。注意**值成员会让完整类型重新外泄**，必须改为指针。
3) 判据：有独立对外接口、可被独立替换/测试的才是模块，目录上表现为 `include/ + src/` 与一个 CMake 目标；不满足的是实现细节，放消费者的 `src/` 下。「只有一个消费者」不构成判据。
4) `role_discovery` 与 `control_plane` 同级：它有自己的对外接口、外部依赖（libsystemd、containerd bridge socket）与设计文档，不是控制平面的实现细节。它与 `control_plane` 目录同级也与其依赖方向一致（`hng_control_plane` 链 `hng_role_discovery`）。
5) `containerd_bridge`（Go module）留在 `role_discovery/` 内，与 `include/`、`src/` 并列：它是独立进程而非私有头，且其 C++ 客户端半边、协议与设计文档都在该模块。
6) `.proto` 只存在于 `proto/`，程序树里只允许出现生成物，不允许 `.proto` 副本。
7) [关于模块的依赖注入](#关于模块的依赖注入)：装配入口（每个模块一个工厂，负责构造与启停时序）属装配期工作，尚未实现。当前具体管理器/发现器头都在 `src/` 下，故暂无途径构造它们。

# 构建体系说明

1) 构建入口是仓库根 `Makefile`，目标 `agent / ebpf / go / test`；`image / package` 待实现。
2) `agent` 转调 CMake 构建 C++ 与 eBPF；`ebpf` 是它的子集（`--target hng_ebpf`）。`main.cc` 为空文件，故暂无 agent 可执行目标（它落地并接入 CMake 后自动包含在内。eBPF 的 hng_ebpf 目标带 ALL，随本目标一并构建。）。
3) C++ 由根 `CMakeLists.txt` 组织，各模块一个 STATIC 库；proto 代码在构建时经 `protobuf_generate` 生成到构建目录。
4) eBPF 由 `kernel/CMakeLists.txt` 负责：clang 编探针、bpftool 生成骨架，产物落源码树 `kernel/<n>.skel.h` 与 `kernel/build/`（均被 .gitignore 覆盖）。
5) eBPF骨架名必须显式给 `<n>_collector`：bpftool 默认名只去 `.o` 扩展名，得 `files_bpf`，与 `collector.hpp` 引用的 `files_collector` 不符。
6) clang 或 bpftool 缺失时 eBPF 目录只跳过，不使整体构建失败；`hng_ebpf` 为空目标，故 `make ebpf` 仍可用。
7) 探针的 `DEPENDS` 含全部共用头，改头即触发重编，避免骨架静默沿用旧 BTF。
8) Go 各 module 独立 `go build`，产物落 `bin/`。构建前须先生成 proto 产物（需 `protoc`、`protoc-gen-go`，proto 内有 service 时另需 `protoc-gen-go-grpc`）
9) include 一律基于仓库根目录（如 `agent/util/include/...`、`agent/role_discovery/src/...`、`kernel/include/...`）；路径里的 `include/` 与 `src/` 段本身就标明了该头的可见性，不再使用 `./include/...` 这类模块内相对写法。
10) 代码生成的产物一律不入库：C++ 侧落构建目录（`build-agent/generated/`），Go 侧落消费方模块内被 .gitignore 覆盖的目录，两者都由构建/生成脚本产出。

# Rolediscovery 模块

1) 角色的进程补漏部分（特别是对于守护进程），依赖 cgroupv2 路径中的进程组；对于 systemd，由于 cgroupv2 的设计，那些由 systemd 启动并管理的单元（.service）的进程会被分到一个叶子 cgroup 中，这使得该 cgroup 路径能给出只属于该角色的所有进程。但对于 .scope 单元，这种要求无法得到保证。  

2) 进程补漏读取的是 cgroup TGID，日后如果扩展至线程需要考虑修正。  

3) systemd 角色发现器：dbus事件流一侧是单调的，无乱序问题，但由于判定是否产出观察量的依据——MainPID和ActiveState取自两个接口（同一个流上的两个独立事件），可能不属于同一时刻

4) role_discoverer.hpp 疑似为冗余设计。它目前并不能称之为接口，其接口方法只由实现者自己调用，只能算基类。故暂时将它放在 src 下。

5) 该模块的 include 理应只由 RoleManager 使用！

# 关于模块的依赖注入

一些模块通过抽象接口使用了其他模块的功能（如模块使用由控制平面实现的XXX_service接口），一些模块通过抽象接口来获得某种服务（例如模块实现控制平面的role_lifecycle_sink，用于接收角色生命周期通知，这时控制平面是接口的使用者）。   
这是当前项目抽象接口的两种用法，有两个问题：1、最终 main.cc 里装配模块时，要同时处理也许越来越复杂的依赖注入。2、经过重构后，具体模块类的注入方法也被隐藏，使得目前没有途径能够完成装配。  
考虑为每个模块设置一个工厂，是公共头文件，各自定义该模块对象的生成与装配（初始化）？最后由 main.cc 直接调用工厂方法。
